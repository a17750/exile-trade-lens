# 当前功能边界与项目复盘

## 结论

项目已经具备可用扩展的完整骨架，但此前的开发节奏偏向“页面出现一个例子，就在现有逻辑上补一个分支”。这种方式短期见效，长期会让物品、词缀、页面 UI、漏译采集和启动时序相互影响。后续开发以稳定契约和回归用例为先，不再以单个截图代表一类问题已经解决。

截至 `edd255e` 基线，自动门禁全部通过；覆盖率报告为物品 99.92%、词缀 87.26%、静态数据 100%，质量阻断项为 0。这些数字只表示数据映射覆盖，不代表真实页面冷启动和交互已经通过。真实交易站验证仍是交付门槛。

## 当前功能分层

| 层 | 职责 | 准确性要求 |
| --- | --- | --- |
| 数据源与构建 | 合并官方英文接口、台服稳定 ID、只读 GGPK、锁定第三方数据和人工审核项 | 不猜测；来源、英文原文和稳定键必须可追溯 |
| 页面 API 翻译 | 翻译 `items`、`stats`、`static`、`filters` 和 `/fetch` 响应 | 物品与词缀必须完整命中；不允许残缺拼接 |
| 页面 UI 翻译 | 翻译按钮、标题、分组和提示文字 | 可使用受控的精确词典兜底，要求低于游戏语义 |
| 漏译采集 | 收集稳定、可复现且不含用户输入的缺失项 | 宁可漏报，不记录输入、卖家、价格或随机名称 |
| 更新与管理 | 远程词库校验、本地修正、漏译查看与导出 | 更新失败继续使用已验证版本，不执行远程代码 |

## 本次暴露的根因

中文物品搜索依赖 `/api/trade2/data/items` 在进入网页缓存前完成翻译。原实现最多等待词库 3 秒，超时后会把英文目录交给页面。词库稍后即使加载成功，页面仍继续使用已经缓存的英文目录，因此表现为“显示翻译可能正常，但中文搜索突然失效”。

旧 smoke test 在执行请求前同步注入了完整词库，只覆盖了稳定运行状态，没有覆盖扩展重新加载后的冷启动时序。这说明“测试通过”与“真实页面可用”之间缺少一层关键契约，而不是又缺一个物品名称特例。

修复原则是：`items`、`stats`、`static`、`filters` 属于页面生命周期基础目录，必须等配置就绪；其他 API 仍保留超时，避免无关请求无限等待。`scripts/search-cold-start-test.mjs` 使用可控时钟固定复现该竞态。

真实页面随后证明“目录已翻译”仍不等于“中文可以检索”：官网原生下拉使用条目的 `name/type` 做过滤，而显示使用 `text`。第一次方案试图修改 Vue multiselect 的私有 watcher；真实生产页没有暴露 `__vue__`，测试中的模拟结构与线上结构不一致，因此该模块已完整删除，不能继续作为兼容层保留。

当前方案只保留一个可验证闭环：`/data/items` 响应中的已确认 `name/type` 被改成“繁中（官方英文）”可逆别名，让官网原生筛选直接命中中文；别名与英文建立精确映射；`/api/trade2/search/` 请求发出前只还原 `query.name/query.type`，其他筛选与排序保持不变。还原索引直接由当前正式词库预先建立，不能依赖本页是否观察过 `/data/items` 响应，因为官网缓存可能绕过该响应拦截。无法解析或与正式译文不完全一致的请求原样放行，禁止按括号猜测还原。自动回归同时断言冷目录场景、中文别名存在、官网请求仅含原始英文及非目标字段未改变；真实页面仍是最终门槛。

官网会把 `/data/items`、`/data/stats`、`/data/static` 和 `/data/filters` 分别缓存为 `items`、`stats`、`data`、`filters`。只刷新扩展不会使官网重新请求目录；这不但会让中文物品检索继续使用旧索引，也会让下拉选项展开时被 DOM 兜底临时翻译、选中后又从旧英文模型重新渲染。

运行时用 `poe2zh-trade2-catalog-schema` 记录自身翻译目录结构版本。版本变化时只删除上述四类官网目录及各自的过期键一次，不清理搜索历史、账号、设置或其他站点数据。回归测试必须证明八个精确键被删除、版本标记写入，同版本再次加载不重复清理。所有被扩展改写的官网目录必须作为一个缓存一致性单元维护，不能再按截图中的单个选项修补。

## 此前方式的问题

1. 个例替代分类。一个 `Superior Bombard Crossbow`、一个魔法装备或一个属性文本，只能证明存在问题，不能直接决定通用规则。
2. 数据问题和运行时问题混在一起。词库完整不等于接口拦截、上下文桥接和页面缓存都正确。
3. 测试过于理想化。同步注入词库掩盖了 service worker、跨上下文传递和扩展重载的时序。
4. 生成文件混入功能差异。重新构建会刷新官方快照、顺序、版本和哈希，必须与运行时代码提交分开审阅。
5. 功能不断叠加。上一个回归未在真实页面确认前继续加入模板，会扩大故障面并降低定位效率。

## 后续变更纪律

每个问题按以下顺序处理：

1. 先定义问题类别和不变量，不直接修改个例。
2. 写出能在修复前失败、修复后通过的最小回归用例。
3. 一次只修改一个层级；运行时代码、翻译数据和生成快照原则上分开提交。
4. 执行回归技能，任何失败都阻断交付。
5. 重新加载扩展并刷新真实交易页，分别检查物品搜索、筛选项、属性词缀和结果卡。
6. 真实页面未验证前，不开始下一项翻译能力扩展。

## 下一阶段优先级

- P0：保证中文物品搜索冷启动稳定，完成真实 Chrome 验证。
- P1：为物品、筛选项、属性/词缀建立固定页面样本和可重复验收记录。
- P1：把生成数据刷新与运行时代码变更拆成独立流程，避免无关大 diff。
- P2：继续完善可信翻译来源和审核队列；不以覆盖率为由引入猜译。
- P2：再评估普通物品展示模板，不恢复尚未验证的实验批次。

在 P0/P1 完成前，不继续扩展新的名称组合或启发式翻译规则。

## Stat 渲染模块拆分

`extension/page/stat-rendering.js` 独立承担模板形状匹配和已验证 `renderings` 选择；`trade-hook.js` 只负责请求拦截、ID 关联和数值替换。后续新增单复数、标点或官方特殊句式时，只能在 `data/verified-stat-renderings.zh-TW.json` 登记同一 stable ID 的证据，再由这个模块处理，不把渲染分支散落回拦截器。
