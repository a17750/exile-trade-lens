# 翻譯準確性審計與禁止猜譯規則

最後更新：2026-08-29

本文件是本專案的準確性基線。翻譯的第一優先級是「不錯配、不臆測、不因追求覆蓋率而產生錯誤中文」。當證據不足時，保留英文並上報，優先於顯示一個看似合理但可能錯誤的譯文。

## 0. 問題處理原則

**提出的問題都不應以個例處理。** 使用者提供的字串、物品或搜索頁只是一個可重現樣本，不是修復範圍。每次處理翻譯問題都必須先找出共同的資料領域、來源、匹配規則和受影響集合，再修正產生該類結果的管線或運行時規則。

具體要求：

1. 禁止只為報告中的英文、搜索 ID 或單件物品增加特判。
2. 報告樣本必須轉成回歸測試，但測試還要包含同類正例、失敗邊界和反例。
3. 修復前要說明該問題影響哪一類資料；修復後要驗證整類輸入，而不是只驗證原始樣本。
4. 單筆人工覆蓋只允許用於有官方證據的真正例外，不能用來掩蓋資料提取或匹配規則缺失。
5. 中英文殘片拼在同一譯文中屬於錯誤翻譯，不計為部分成功或覆蓋率提升。

## 1. 審計結論

目前程式沒有把 `glossary` 的 `proposed` 術語或候選結果直接寫入運行詞庫；候選只出現在建置報告的 review queue。已發現並收緊以下三種會造成錯譯的推斷路徑：

| 路徑 | 原本風險 | 現在規則 |
|---|---|---|
| `/fetch` stat 的 `hashes` 與 mod 陣列 | 只按位置可能把相鄰詞條數值交叉套用 | 先用 ID 對應的英文模板驗證，再用完整英文模板反查；無法唯一確認就保留英文 |
| 隨機名稱組件 DP | 多種拆法時自動選最少片段，結果可能是猜的 | 只有唯一完整組合才翻譯；存在不同組合就保留英文 |
| `typeLine` 基礎類型替換 | 完整名稱失敗後只替換底材，會產生大批中英混排 | 複合名稱只有完整、唯一可翻譯時才翻譯；否則整段保留英文 |
| 普通品質 `typeLine` | `frameType=0` 不在既有魔法/稀有分支，導致 `Superior Bombard Crossbow` 既未翻譯也未上報 | 只按官方 `ClientStrings.QualityItem` 完整模板翻譯；未知模板保留英文並上報 |
| 物品目錄缺少 `text` | 基礎物品只有 `type`，雙語格式化輸出 `譯文 (undefined)` | 以 `text ?? name + type` 重建英文，且格式化器禁止輸出空英文 |
| 輸入派生下拉 | 輸入文字被框架渲染到 body 浮層，不是 input 後代，舊 DOM 掃描誤當 UI | 獨立策略模組按可編輯控件、ARIA 關聯、輸入時間和穩定性拒絕 |
| `/data/items` 名稱與類型組合 | 只命中 `name` 或 `type` 時仍輸出殘缺中文 | 輸入中存在的所有組成部分都命中後才組合；否則保留完整英文 |
| `Mods.Name` 跨領域合併 | 怪物和裝備可能使用相同英文但不同繁中，例如 `Frosted` | 魔法裝備名稱只採用 `Domain=ITEM`；其他領域隔離，英文多譯鍵排除並報告 conflict |
| DOM 扁平 `exact` 字典 | 同一英文在不同領域有不同中文時，後寫值覆蓋前寫值 | 發現衝突即從 DOM 索引移除，保留原文 |
| 舊版遠程 stat 詞庫 | 缺少英文模板時無法驗證 ID 與顯示文字 | 遠程資料缺少模板即拒絕更新；合併時保留內置模板 |
| stat 目錄模板與 `/fetch` 特殊文案 | 100% 等特殊值可能把 `#% chance...` 渲染成 `Always...`，形狀校驗會正確拒絕但留下英文 | 建立 stable-ID 限域的官方渲染變體；只接受英台 `/fetch` 同 hash 證據，不加入全局 exact |
| `/fetch` 單件字段異常 | 新增字段解析若拋錯，整批 response 不寫回，所有結果看似失去翻譯 | 每件物品在副本上原子翻譯；單件失敗只回退該件英文，不影響同批其他結果 |

## 2. 目前允許自動採用的證據

只有以下情形可以進入擴展的正式運行資料：

1. 官方 Trade API 的相同穩定 ID，且英文/繁中佔位符數量一致。
2. 同一版本 `Content.ggpk` 中英表按穩定行鍵配對，並通過表指紋和幾何校驗。
3. 人工覆蓋，且穩定 ID 記錄包含仍有效的 `expectedEnglish`。
4. 已鎖定版本、英文完整匹配、沒有專案衝突的第三方名稱補缺。這不是模糊匹配，但仍會保留來源和衝突報告。
5. 完整英文詞組的唯一精確對照。

第三方補缺即使是大小寫與空白規範化後的精確匹配，也不代表語義已由專案人工確認；它不能被複製成新的人工正式翻譯，後續若發現衝突必須進入 review。

## 3. 明確禁止的行為

以下邏輯不得用於正式翻譯或覆蓋已有譯文：

- 編輯距離、相似度、前綴/包含關係或「看起來像」的模糊匹配。
- 按陣列位置、接口返回順序或跨版本行號推斷對照。
- 把英文名稱拆成普通單字後，使用未審核術語自動拼接。
- 把一個領域的翻譯（例如 `base-item`）套用到另一個領域（例如隨機 `name` 或 stat）。
- 用相鄰詞條、上一條結果或共用索引補足當前詞條數值。
- 在翻譯失敗時只顯示部分中文，讓使用者誤以為整句已確認。
- 用 AI、候選分數或 `confidence` 直接決定正式譯文。
- 為了提高 coverage 而刪除 association mismatch、source conflict 或 semantic change 報告。

## 4. 各程式模組的審計結果

### 4.1 `scripts/lib/translation-engine.mjs`

`createCandidateEngine` 只服務 `review-queue.json`。`proposed` 術語會標記為 `needs-review`，候選包含證據但不寫入 `bundled.json`。未來修改時必須維持這個邊界。

### 4.2 `scripts/build-data.mjs` 與官方資料合併

`stats.entries[id]` 現在會同時保存 `english` 模板和 `text` 繁中模板。建置期使用穩定 ID、佔位符檢查和 `expectedEnglish`；不得在此處用候選分數替換正式欄位。

`data/verified-stat-renderings.zh-TW.json` 專門記錄「目錄模板以外、但已由英台官方 `/fetch` 證明」的顯示變體。構建會檢查 stable ID 存在、目錄英文未漂移、兩端 evidence hash 相同、佔位符一致及變體無衝突。它不會改寫主模板，也不會把變體放進全局精確詞典。

### 4.3 `extension/page/trade-hook.js`

`/fetch` 的 stat 翻譯先在當前 ID 的官方渲染變體中匹配，再採用「ID 英文模板 + 當前英文詞條」雙重確認。`#` 只代表模板佔位符，數值始終從當前英文詞條提取。變體不能跨 ID 使用；找不到唯一候選時觸發 `fetch:<kind>:association-mismatch`，不翻譯。

`/fetch` 的每件物品在獨立副本上翻譯，完成後才替換原 item。任一可選字段形狀異常時只回退該件完整英文，不能讓整個 response 放棄寫回。`grantedSkills` 等尚未建立完整領域流程的字段不在本輪順帶接入。

稀有名稱只允許在完整名稱可由 GGPK Words 組件唯一覆蓋時拼接。魔法 `typeLine` 使用 `Mods.Id` 穩定配對得到的 `Domain=ITEM` 前後綴，並按「前綴 + 底材 + 後綴」重建。多解或缺少任一組件時整段保留英文；不得只替換其中的基礎類型。

普通物品 `typeLine` 不使用魔法前綴域。品質文字使用 GGPK `ClientStrings` 的穩定 ID
`QualityItem`，即 `Superior {0} -> 精良的 {0}`。只有原文完整符合模板且 `{0}` 的底材有官方譯文时
才输出中文；未知普通展示模板会以 `fetch:typeLine:normal-display-unresolved` 进入自检。结果卡片仍排除
DOM 平面扫描，因为它缺少 `frameType/baseType` 结构；报告由 `/fetch` 结构化数据层负责。

### 4.4 `extension/content/bridge.js`

DOM 翻譯是最後的 UI 顯示兜底，不是資料解析器。結果卡片不走扁平 DOM 翻譯；扁平索引遇到同英文多個不同譯文時直接放棄該鍵，避免跨領域誤套。

### 4.5 `extension/background/service-worker.js`

遠程詞庫必須通過 schema、SHA-256 和 stat 英文模板驗證。合併舊資料時，不得用缺少 `english` 的遠程 entry 覆蓋內置模板。人工修正仍需通過 `#` 數量檢查並保留本地來源。

### 4.6 歷史正式詞庫與第三方補缺的邊界

`data/translations.zh-TW.json` 是一次性遷移的歷史詞庫，檔案級別有來源指紋，但不是每一筆都帶獨立的人工審核證據。它目前作為專案既有基線使用；新增或改動不得把它當成「自動推測」的依據。

`poe-game-data` 的補缺使用鎖定 commit 和規範化後的完整英文相等匹配，不是模糊猜測；但它仍是第三方譯文，與專案已有譯文衝突時只進入 review。若未來要進一步追求零偏差，可把所有第三方補缺從運行資料降級為 review 候選，不能默認視為人工確認。

## 5. 自檢輸出分類

漏譯報告必須區分：

- `missing-translation`：沒有任何可用對照。
- `association-mismatch`：有候選 ID，但與當前英文詞條不一致。
- `source-conflict`：官方、第三方或專案資料互相衝突。
- `semantic-change`：官方英文在版本間發生變化，舊譯文尚未重審。

這些類型不能合併成普通「可能翻譯」，也不能在自動更新時靜默清除。

## 6. 修改程式前的準確性檢查清單

每次涉及翻譯邏輯的修改，都要回答：

1. 這筆資料的領域和穩定鍵是什麼？
2. 對照來自哪個可追蹤版本？是否有英文原文可驗證？
3. 是否可能存在兩個以上候選？若有，程式是否保留英文？
4. 數值、符號、佔位符和原文是否逐項對應？
5. 該邏輯是否可能跨領域、跨版本或依賴陣列位置？
6. 失敗時是否會產生可定位的報告，而不是靜默猜譯？
7. 是否新增了故意錯序、重複組件、多解組合或衝突鍵的回歸測試？
8. 修復針對的是共同原因還是報告樣本？是否掃描並驗證了同類輸入？
9. 輸出是否包含「已翻譯片段 + 未翻譯英文片段」？若有，必須視為失敗並整段回退英文。
10. 同名記錄是否跨越 `ITEM`、`MONSTER`、`AREA` 等 Mods 領域？若是，是否已分域或排除？

最低驗證命令：

```powershell
node scripts/build-data.mjs
node scripts/check-quality.mjs
node scripts/pipeline-test.mjs
node scripts/smoke-test.mjs
node scripts/background-smoke-test.mjs
node scripts/bridge-context-smoke-test.mjs
```

## 7. 對後續開發的硬性要求

任何新翻譯來源都必須先加入「來源、版本、領域、穩定鍵」再接入建置器；任何新匹配器都必須先定義「唯一匹配條件」和「無法唯一匹配時的行為」。如果不能證明翻譯與原文一一對應，就不能自動顯示中文。

歷史腳本的可借鑑行為與禁止重新接入的邊界見 [`trade.js` 歷史處理方式備忘](TRADE-JS-REFERENCE.md)。

## 8. 漏譯導出的固定詞准入

漏譯導出是待審輸入，不是可直接追加到通用詞典的翻譯來源。每批導出必須先按共同原因分類：

1. 已存在於其他資料域的鍵：只有確認該詞本身就是目標域的正式標籤，才提升到領域詞典；不得在運行時對整張 `exact` 表做跨域兜底。
2. 穩定屬性標籤：確認繁中術語後寫入 `data/verified-labels.zh-TW.json`，並記錄審核日期和輸入批次。
3. 純 UI 按鈕、提示語、空狀態和聯盟選單文字：允許使用經人工快速檢視的直譯，不必等待官方繁中來源。仍需保留格式、占位符和產品名稱，不得把物品結果或玩家輸入誤判為 UI。
4. 完整隨機物品名和其他遊戲資料：必須使用結構化規則或穩定 ID，不得逐條硬編碼。
5. 上下文不足的記錄：保留待審，先擴充採集欄位；不得以名稱外觀推斷資料域。

`poe2zh-missing-2026-08-28.json` 的審核將 22 個穩定物品屬性、2 個無歧義 UI 標籤和 12 個一般界面直譯納入 `verified-labels.zh-TW.json`。`Frosted Recurve Bow of Osmosis`、`Ezomyte Buckler` 和 `Ezomyte Quarterstaff` 仍未被當作固定 UI 寫入。這個處理是同類規則，不是樣本特判。

### UI 與遊戲資料的準確性分級

- 高要求：物品名稱、基底、前後綴、屬性數值、stat、技能與遊戲機制。只接受可驗證的一一對照，失敗時保留英文。
- 低要求：按鈕、面板標題、操作提示、搜尋空狀態、說明 tooltip 和聯盟選單顯示文字。允許人工直譯或一般翻譯來源，目標是易懂和完整覆蓋。
- 邊界判斷：文字只要出現在結果卡、物品 API 字段或玩家輸入相關節點，就不能因為它同时出现在下拉框中而降級成低要求 UI。
