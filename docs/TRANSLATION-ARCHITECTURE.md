# 中英对照与数据架构

最后更新：2026-08-28

## 架构原则

`trade.js` 只作为历史实现和翻译内容的参考资料：

- 扩展运行时不得加载、导入或执行 `trade.js`。
- 正式构建不得要求工作区存在 `trade.js`。
- 不得从 `trade.js` 截取代码生成扩展运行文件。
- 不得把 `trade.js` 当作持续更新的中文数据源。
- 如需保留其中已有译文，应进行一次性迁移，写入本项目自有、可审查的数据文件，并标注来源为历史参考。

## 当前实现的真实情况

从版本 `0.2.6` 开始，迁移已经完成：

1. 历史译文只进行过一次性导出，现保存于 `sources/translations.zh-TW.json`。
2. `scripts/build-data.mjs` 不读取、执行或解析根目录参考脚本。
3. `extension/page/ajax-hooker.js` 是独立维护的固定运行文件，构建器不会生成或修改它。
4. 生成词库的 `source` 为项目自有翻译文件，版本为 `project-zhTW-*`。

根目录参考脚本即使被移走，数据构建和测试仍可正常完成。

## 当前中英对照如何形成

```text
POE2 官方交易接口（英文、当前结构、稳定 ID）
                    │
                    ├── 按 ID 对齐
                    │
台服官方交易接口（繁中、同一稳定 ID）
                    │
                    ├── 校验占位符后优先采用
                    │
sources/translations.zh-TW.json（项目自有基础译文）
                    │
                    ├── 合并物品、词缀、筛选器、静态项目
                    │
sources/manual-overrides.json
                    │
                    └── 修复第三方缺失或语义过期项
                                   ↓
                    extension/data/bundled.json
```

运行时的优先级是：

```text
用户本地修正
  > 下载并校验过的远程词库
  > 扩展内置词库
  > 英文原文
```

当前还会生成一个 `exact` 表，用于把动态 DOM 中的英文标签直接映射到中文；接口响应本身则优先按稳定 ID 翻译。

## 后续仍需改善的问题

### 一次性迁移的数据仍需要逐步替换

代码与构建依赖已经解除，但迁移进来的译文本身仍是历史快照。未来应按领域逐步换成带固定版本和来源信息的数据，并保留人工审核记录。

### 台服数据仍可能落后于国际服

台服官方源已接入，但当前 `stats` 数量仍少于国际服。构建只采用双方共有的稳定 ID；台服缺失项继续回退，不会清空项目已有译文。例如 `map_magic_monsters` 已由台服官方确定为“怪物效用”。

### `names/tw.json` 不是完整交易词库

`poe-game-data/poe2/names/tw.json` 主要是基础物品和技能名称的派生字典，不覆盖完整的交易筛选器、UI、属性说明和所有词缀，不能作为唯一数据源。

### 当前输出缺少细粒度来源信息

最终 JSON 能完成翻译，但不能对每条记录回答“来自哪个仓库、哪个版本、按什么键匹配、是否人工审核”。这会降低自动更新的可信度。

## 理想架构

### 1. 扩展代码完全自有

- `extension/page/trade-hook.js`：只负责读取自有数据结构并翻译官方响应。
- 请求接管器使用本项目独立维护的实现，或引入有明确来源、版本和许可证的上游库。
- `extension/page/ajax-hooker.js` 不再由 `trade.js` 生成。
- 运行代码和翻译数据分离，远程更新永远只能替换 JSON 数据。

### 2. 官方英文接口作为事实基准

每次构建获取：

- `/api/trade2/data/items`
- `/api/trade2/data/stats`
- `/api/trade2/data/static`
- `/api/trade2/data/filters`

官方接口决定当前存在的 ID、英文文本、组选项和页面结构。中文源不能自行创建已经不存在的官方 ID。

### 3. 中文数据按领域组合

建议的数据来源和职责：

| 层级 | 内容 | 建议来源 |
|---|---|---|
| A | 交易词缀、静态数据、筛选器与选项 | 国际服英文 API + 台服繁中 API，按稳定 ID 配对 |
| B | 基础物品、技能名称 | 台服可安全配对条目 + `poe-game-data` 的 `names/tw.json` |
| C | 第三方修饰词补充 | `poe-game-data` 的 modifiers 数据，按内部 ID 或英文模板配对 |
| D | 固定网页 UI | 本项目 `ui.zh-TW.json` |
| E | 术语统一 | 本项目 `glossary.zh-TW.json` |
| F | 缺失与语义变更 | 本项目 `manual-overrides.json` |

第三方地址应固定到 tag 或 commit SHA，不应在正式发布中直接追踪 `master`，否则相同版本号可能得到不同内容。

### 4. 本项目拥有规范化源文件

当前规范源文件是：

```text
sources/
  translations.zh-TW.json
  manual-overrides.json
```

`translations.zh-TW.json` 是一次性迁移后由本项目接管的基础词库；其 `provenance` 只说明历史来源，不会触发任何外部读取。今后可以在不改变生成数据格式的情况下继续拆分为：

```text
sources/
  ui.zh-TW.json
  glossary.zh-TW.json
  trade-filters.zh-TW.json
  manual-overrides.json
  source-lock.json
```

- 新构建不读取历史参考脚本；未来译文修改只能发生在上述结构化文件或已锁定的外部数据中。
- `source-lock.json` 保存外部来源 URL、commit/tag、下载时间和 SHA-256。

### 5. 合并时优先按稳定键

推荐优先级：

```text
已审核人工覆盖（稳定 ID + expectedEnglish）
  > 台服官方同稳定 ID 本地化数据
  > 项目已有正式译文
  > 规范化英文名称对照
  > 术语表和精确 UI 对照
  > 英文回退
```

仅使用英文字符串匹配时必须进行统一规范化，但不能用模糊匹配自动提交译文。模糊候选只能进入待审核报告。

### 6. 构建必须产生质量报告

构建阶段检查：

- 当前官方 ID 的中文覆盖率。
- 新增、删除和英文语义变化的 ID。
- 中文值为空、仍完全为英文或与英文相同的项目。
- `#` 数值占位符数量是否一致。
- 下拉选项 ID 是否完整对应。
- 同一英文映射到多个中文、同一 ID 被多个来源覆盖的冲突。
- 人工覆盖中的 `expectedEnglish` 是否仍与官方接口一致。

输出建议包括：

```text
dist/dataset.json
dist/manifest.json
dist/coverage-report.json
dist/review-queue.json
```

只有数据集和清单会被扩展下载；质量报告用于 GitHub Actions 和人工审核。

### 7. 运行时自检只负责发现，不负责猜译

- 接口层记录缺少翻译的稳定 ID 和官方英文。
- DOM 层记录限定区域中的残留标准 UI 英文。
- 本地去重、计数和导出，不自动上传用户页面数据。
- 自动更新后重新消解已补齐项目。
- 机器翻译或模糊匹配只能生成候选，必须人工确认后进入正式覆盖表。

## 迁移状态

### 阶段一：解除代码依赖（已完成）

1. 确认 `ajaxHooker` 的原始上游、版本和许可证；无法确认时改写最小请求接管器。
2. 将 `extension/page/ajax-hooker.js` 变为项目自有的固定源码。
3. 删除 `build-data.mjs` 中截取 `trade.js` 代码的逻辑。

### 阶段二：一次性迁移历史译文（已完成）

1. 使用当前 `trade.js` 最后执行一次只读导出。
2. 将结果保存为 `sources/translations.zh-TW.json`，由项目正式接管维护。
3. 保存来源说明、旧版本号、导出日期和 SHA-256。
4. 后续构建不得再读取 `trade.js`。

### 阶段三：建立独立数据管线（核心流程已完成）

1. [x] 获取并保存官方英文接口快照和审核基线。
2. [x] 将 `poe-game-data` 锁定到 commit 和 SHA-256。
3. [x] 应用完整短语、领域术语、人工覆盖和名称精确匹配。
4. [x] 输出覆盖率、冲突、质量门禁和待审核报告。
5. [x] 接入台服官方繁中交易接口，按稳定 ID 自动合并并输出来源报告。
6. [ ] 继续接入 modifier 等领域数据，并积累术语审核样本。

### 阶段四：自动发布

1. GitHub Actions 定时或手工运行构建。
2. 数据发生有效变化且质量门禁通过后发布新版本。
3. 插件通过固定 GitHub Raw 或 jsDelivr 地址获取清单。
4. SHA-256 验证通过后才替换本地词库；失败继续使用旧版。
